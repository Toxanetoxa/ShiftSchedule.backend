# ShiftSchedule API

Сервис графиков смен на Laravel и PostgreSQL. API возвращает календарь сотрудников, сохраняет назначения одним атомарным пакетом и создаёт неизменяемые публикации выбранного периода. Клиентское приложение подключается отдельно по HTTP; Swagger UI предоставляет страницу документации и ручной проверки API.

Реализованы назначение шаблона или своей смены, очистка и перенос назначений, проверка пересечений, контроль версии графика, подсчёт запланированных минут и покрытия по дням. Изменения становятся опубликованными только после отдельного запроса публикации.

## Локальный запуск

Нужны Docker Engine с Compose v2 и работающий Docker daemon, например Docker Desktop. Make необязателен. Все команды ниже выполняются **из корня этого репозитория**, где лежат `compose.yaml`, `Makefile` и `artisan`.

При первом запуске создайте локальные настройки и запустите сервисы:

```sh
cp .env.example .env
make up
```

Если `.env` уже существует, сохраните его настройки и пропустите копирование. `.env.example` — общий шаблон; локальный `.env` в Git не хранится.

Без Make:

```sh
cp .env.example .env
docker compose up -d --build --wait --remove-orphans
```

Compose запускает сервис `db` (контейнер `postgres`), дожидается его готовности и запускает `app` (контейнер `backend`). Первый запуск требует интернета для Docker-образов и Composer-пакетов и может занять несколько минут.

| Адрес по умолчанию | Назначение |
| --- | --- |
| [http://localhost:8000/api/v1](http://localhost:8000/api/v1) | JSON с названием и статусом сервиса |
| [http://localhost:8000/up](http://localhost:8000/up) | Проверка загрузки Laravel; используется healthcheck контейнера |
| [http://localhost:8000/docs](http://localhost:8000/docs) | Swagger UI и выполнение запросов |
| [http://localhost:8000/docs/openapi.json](http://localhost:8000/docs/openapi.json) | OpenAPI для Postman и генераторов клиентов |
| `127.0.0.1:5432` | PostgreSQL для локального SQL-клиента |

Проверить запуск:

```sh
make ps
curl -H 'Accept: application/json' http://localhost:8000/api/v1
curl -H 'Accept: application/json' http://localhost:8000/up
```

`/up` проверяет запуск приложения; отдельной проверки доступности БД в этот маршрут не добавлено. Календарный запрос ниже проверяет и работу с данными.

## Что происходит при локальном старте

`docker/php/entrypoint.sh` выполняется при каждом старте контейнера приложения:

1. Создаёт `.env` из `.env.example`, если локального файла ещё нет, и необходимые каталоги кеша, сессий, шаблонов и логов.
2. Выполняет `composer install` из lock-файла, синхронизируя постоянный том `vendor` с текущим кодом.
3. Очищает кеш конфигурации и генерирует `APP_KEY`, только если ключ отсутствует. Уже заданный ключ сохраняется.
4. Запускает `php artisan app:initialize`: применяет новые миграции и выполняет сиды.
5. Запускает HTTP-сервер Laravel на порту `8000`.

`app:initialize` работает только с PostgreSQL. На время миграций и сидов удерживается PostgreSQL advisory lock, поэтому несколько экземпляров с одной БД не выполняют инициализацию одновременно. Миграции запускаются перед сидированием; все сиды выполняются в транзакции. Если этап завершится ошибкой, HTTP-сервер не запустится.

Сиды идемпотентны: повторный запуск добавляет отсутствующие исходные записи и сохраняет изменённые имена, порядок, активности, версию графика, назначения и публикации. Исключение — пустые аватары восьми исходных сотрудников: они заполняются автоматически. Смены и публикации сиды не создают и не восстанавливают после очистки. Сидирование выполняется при старте независимо от `SCHEDULE_DEMO_MODE`; этот флаг управляет доступом к API.

Повторить инициализацию вручную:

```sh
make artisan ARGS="app:initialize --no-interaction"
```

### Подключение к PostgreSQL и хранение данных

Внутри Compose приложение подключается к `db:DB_PORT`, с компьютера — к `127.0.0.1:DB_PORT`. Для DataGrip, DBeaver или psql используйте имя БД, пользователя и пароль из своего `.env`. Не указывайте `db` как hostname в SQL-клиенте, работающем на компьютере.

Если порт `5432` занят, измените `DB_PORT`, например на `5433`, и выполните `make up`. Текущая конфигурация меняет **и опубликованный, и внутренний порт** PostgreSQL; healthcheck и Laravel используют это же значение.

Оба опубликованных порта привязаны к `127.0.0.1`: они доступны локально, а не всему интернету. Данные PostgreSQL 18 хранятся в томе `postgres_data`, смонтированном в `/var/lib/postgresql`, зависимости PHP — в томе `vendor`. Исходники примонтированы из текущего каталога.

Изменение `DB_USERNAME`, `DB_PASSWORD` или `DB_DATABASE` в `.env` не переименует и не перенастроит уже инициализированную БД: соответствующие изменения нужно внести и в PostgreSQL. `make down` сохраняет тома. **`docker compose down -v` удаляет тома вместе с данными БД**; для обычного перезапуска эта команда не нужна.

## API и доступ

Все операции графика работают в демонстрационном режиме: `SCHEDULE_DEMO_MODE=true` разрешает только UUID исходного графика, а автор публикаций задаётся как `demo-manager`. Другой UUID или выключенный режим возвращает `404 SCHEDULE_NOT_FOUND`. Пользовательская аутентификация и разграничение прав ещё не реализованы; маршрут регистрации, входа и Bearer-токены отсутствуют.

CRUD сотрудников, шаблонов и графиков, список публикаций и удаление публикаций в текущий API не входят.

| Метод | Путь | Результат |
| --- | --- | --- |
| `GET` | `/api/v1` | Название и статус сервиса |
| `GET` | `/api/v1/schedules/{scheduleId}/calendar` | Календарь за `[from, to)` |
| `PATCH` | `/api/v1/schedules/{scheduleId}/cells` | Атомарное сохранение набора ячеек |
| `POST` | `/api/v1/schedules/{scheduleId}/publications` | Публикация версии за выбранный диапазон |
| `GET` | `/api/v1/schedules/{scheduleId}/publications/{publicationId}` | Метаданные и неизменяемый снимок |
| `GET` | `/up` | Проверка загрузки Laravel |

Передавайте `Accept: application/json`, а для записи — также `Content-Type: application/json`. JSON использует `camelCase`. `expectedVersion` и `endDayOffset` должны быть числами, не строками. Неизвестные поля в запросах записи отклоняются.

### Чтение календаря

```sh
curl --get \
  'http://localhost:8000/api/v1/schedules/00000000-0000-4000-8000-000000000001/calendar' \
  -H 'Accept: application/json' \
  --data-urlencode 'from=2026-11-09' \
  --data-urlencode 'to=2026-11-16'
```

Период включает `from` и исключает `to`; допустимо от `1` до `62` дней. Даты передаются в формате `YYYY-MM-DD`.

Ответ содержит `schedule` с текущей `version`, `range`, `employees`, активные `shiftTemplates`, назначения `shifts` и `coverage` для каждого дня. Сотрудники без назначений остаются в ответе с `scheduledMinutes: 0`. Поле `isActive` учитывает как активность сотрудника, так и его участия в графике. Чтение выполняется в согласованной транзакции `REPEATABLE READ`.

Ночная смена относится к дате начала `workDate`: её минуты целиком входят в эту дату, а `coverage.shiftCount` считает назначения, начинающиеся в день. `covered` означает наличие хотя бы одного назначения, а не соблюдение отдельного норматива численности.

### Сохранение ячеек

Сначала прочитайте календарь. В примере `expectedVersion: 1` подходит **только для ещё не изменённого графика**; замените его актуальным `schedule.version` из ответа.

```sh
curl -X PATCH \
  'http://localhost:8000/api/v1/schedules/00000000-0000-4000-8000-000000000001/cells' \
  -H 'Accept: application/json' \
  -H 'Content-Type: application/json' \
  --data '{
    "expectedVersion": 1,
    "changes": [
      {
        "employeeId": "00000000-0000-4000-8000-000000000201",
        "workDate": "2026-11-09",
        "shift": {
          "startTime": "07:00",
          "endTime": "15:00",
          "endDayOffset": 0,
          "sourceTemplateId": "00000000-0000-4000-8000-000000000101"
        }
      }
    ]
  }'
```

В `changes` допустимо от `1` до `2000` уникальных пар `employeeId` / `workDate`. Для назначения обязательны все четыре поля `shift`; при своей смене `sourceTemplateId` равен `null`. Для шаблона времена и `endDayOffset` должны совпадать с его текущими значениями. `shift: null` очищает ячейку.

Время задаётся как `HH:mm` в часовом поясе графика, не браузера. `endDayOffset: 0` означает окончание в день начала, `1` — на следующий день. Ночная своя смена может выглядеть так:

```json
{
  "startTime": "22:00",
  "endTime": "06:00",
  "endDayOffset": 1,
  "sourceTemplateId": null
}
```

Допустимая длительность — от `1` до `1439` минут. Несуществующее или неоднозначное локальное время при переходе часового пояса отклоняется. Новые назначения неактивному сотруднику запрещены; очистка существующего назначения разрешена.

Пакет сохраняется целиком либо целиком отклоняется. Для переноса отправляйте в **одном запросе** очистку исходной ячейки и назначение целевой. Пересечения проверяются по итоговому состоянию всех назначений сотрудника, включая другие графики. Смены могут соприкасаться концами, но не пересекаться.

Успешный ответ `200` содержит `version` и `changedCells` с итоговым состоянием переданных ячеек. Реальное изменение увеличивает версию графика один раз за пакет; повторное сохранение того же состояния с актуальной версией её не увеличивает. При устаревшей версии сервер возвращает `409 SCHEDULE_VERSION_CONFLICT`: прочитайте календарь и согласуйте изменения перед следующей записью.

### Публикация

Публикация создаёт снимок **уже сохранённого** графика. Подставьте в `expectedVersion` версию из последнего чтения или сохранения; пример `2` соответствует первому изменению нового графика.

```sh
curl -X POST \
  'http://localhost:8000/api/v1/schedules/00000000-0000-4000-8000-000000000001/publications' \
  -H 'Accept: application/json' \
  -H 'Content-Type: application/json' \
  --data '{"expectedVersion":2,"from":"2026-11-09","to":"2026-11-16"}'
```

Новая публикация возвращает `201` и поля `id`, `scheduleId`, `range`, `sourceVersion`, `publishedAt`. Повтор для той же версии и диапазона возвращает существующую публикацию с `200`, даже если рабочий график уже изменился. Если такого снимка нет, а версия устарела, возвращается `409`. Создание публикации не увеличивает версию графика.

Прочитайте снимок по `id` из ответа, заменив `<publicationId>`:

```sh
curl -H 'Accept: application/json' \
  'http://localhost:8000/api/v1/schedules/00000000-0000-4000-8000-000000000001/publications/<publicationId>'
```

Ответ добавляет `snapshot` с `schemaVersion: 1`, графиком, диапазоном, сотрудниками, сменами и покрытием. Шаблоны в снимок не входят. Последующие изменения графика и сотрудников не изменяют сохранённую публикацию.

### Ошибки

Предметные ошибки возвращаются в формате:

```json
{
  "error": {
    "code": "SCHEDULE_VERSION_CONFLICT",
    "message": "График изменён в другой сессии. Обновите данные перед сохранением.",
    "details": {
      "expectedVersion": 1,
      "currentVersion": 2
    }
  }
}
```

| HTTP | Коды / причина |
| --- | --- |
| `400` | `INVALID_JSON` — синтаксически некорректный JSON |
| `404` | `SCHEDULE_NOT_FOUND`, `PUBLICATION_NOT_FOUND` |
| `409` | `SCHEDULE_VERSION_CONFLICT`, `SHIFT_OVERLAP` |
| `422` | `VALIDATION_FAILED`, `INVALID_DATE_RANGE`, `INVALID_SHIFT_TIME`, `EMPTY_CHANGESET`, `DUPLICATE_CELL_CHANGE` |
| `422` | `EMPLOYEE_NOT_IN_SCHEDULE`, `EMPLOYEE_INACTIVE`, `TEMPLATE_NOT_FOUND`, `TEMPLATE_INACTIVE`, `TEMPLATE_VALUES_MISMATCH` |
| `429` | `RATE_LIMIT_EXCEEDED` — превышен общий лимит IP |
| `500` | `INTERNAL_ERROR` — ошибка маршрута графика; `details.requestId` позволяет найти запись в логе |

Подробные схемы и примеры ответов находятся в [openapi.json](openapi.json). Внутренние исключения маршрутов графика не раскрывают SQL или stack trace клиенту.

## Swagger / OpenAPI

[Swagger UI](http://localhost:8000/docs) описывает все пять операций API и `/up`. Источник контракта — [openapi.json](openapi.json); обновляйте его одновременно с API. Проверки документации сверяют операции с маршрутами и проверяют внутренние ссылки схем.

Для ручной проверки раскройте операцию, нажмите **Try it out**, заполните параметры и нажмите **Execute**. Начните с чтения календаря и его текущей версии. `PATCH` и `POST` действительно меняют данные. UUID публикации берётся из ответа её создания, а не из демонстрационного примера.

Ресурсы Swagger UI устанавливаются Composer-пакетом и раздаются локально. CDN и внешний валидатор спецификации не используются. Swagger отправляет запросы на тот же origin, поэтому отдельная настройка CORS для него не нужна. Документация разделяет лимит запросов с API.

`API_DOCS_ENABLED=false` отключает страницу, OpenAPI JSON и ресурсы документации. После изменения выполните `make artisan ARGS="config:clear --no-interaction"` или `make restart`. Этот флаг не заменяет авторизацию API.

## Ограничение запросов и CORS

### Лимит на IP

Маршруты `/api/v1` и `/docs` используют Laravel `throttle:api` и общий счётчик по IP. Значение по умолчанию — `10` запросов за секундное окно, настраивается через `API_RATE_LIMIT_PER_SECOND`. Успешные и ошибочные запросы, дошедшие до лимитера, расходуют одну квоту независимо от метода. `/up` и обработанные CORS preflight-запросы `OPTIONS` её не расходуют.

При превышении возвращаются `429`, код `RATE_LIMIT_EXCEEDED`, `error.details.retryAfter` и заголовки `Retry-After`, `X-RateLimit-Limit`, `X-RateLimit-Remaining`, `X-RateLimit-Reset`. Клиенту следует учитывать время ожидания.

Счётчики хранятся в кеше приложения. Для нескольких PHP-процессов нужен общий кеш; в этом окружении используется `CACHE_STORE=database`. `array` и `null` не подходят для рабочего лимитера между HTTP-запросами. Удаление кеша сбрасывает счётчики.

По умолчанию список `TRUSTED_PROXIES` пуст: клиент не может просто подменить учитываемый IP заголовком `X-Forwarded-For`. За reverse proxy укажите только его реальные IP/CIDR и настройте корректную передачу адреса клиента. При прямом запросе из браузера API видит публичный IP посетителя; за не настроенным доверенным прокси несколько посетителей могут разделять его лимит. Пользователи одной внешней сети также могут иметь общий IP.

Это ограничение частоты запросов на уровне приложения. Оно использует секундные окна, а не скользящий интервал; при параллельных запросах возможен небольшой выход за лимит. Для публичного сервиса ограничения на reverse proxy/CDN позволяют отклонять нагрузку до выполнения PHP.

### Разрешённые origin

CORS применяется к `/api/*`. Задайте точные origin через запятую, без путей и завершающего `/`:

```dotenv
CORS_ALLOWED_ORIGINS=http://localhost:5173,https://toxanetoxa.github.io
```

Для приложения на GitHub Pages указывается `https://toxanetoxa.github.io`, без пути репозитория. Протокол и порт входят в origin: `http` и `https`, `localhost` и `127.0.0.1`, разные порты — разные источники. Пустое или отсутствующее значение не разрешает межсайтовое чтение из браузера. Для списка конкретных сайтов не используйте `*` или `null`.

Разрешены `GET`, `HEAD`, `POST`, `PATCH`, `OPTIONS` и заголовки `Accept`, `Content-Type`. Preflight кешируется браузером до `600` секунд. JavaScript разрешённого клиента может читать `Retry-After` и `X-RateLimit-*`; передача credentials между origin отключена.

После изменения настройки очистите конфигурацию или перезапустите контейнер. CORS ограничивает доступ браузерного JavaScript к ответам и разрешает preflight, но не является авторизацией и не блокирует curl или Postman. При запросах через прокси на домене клиентского приложения браузерный CORS для этого запроса не требуется.

PostgreSQL обеспечивает составные внешние ключи принадлежности сотрудника и шаблона графику, одну смену на ячейку и отсутствие пересечений сотрудника **между всеми графиками**. SQLite и MySQL не заменяют PostgreSQL для этой схемы.

`work_date` — локальная дата начала, а `starts_at` и `ends_at` — `timestamptz`. Приложение переводит локальное время графика в абсолютные моменты и проверяет длительность с учётом часового пояса. Название и цвет шаблона сохраняются в назначении как снимки.

### Аватары сотрудников

При создании `Employee` через Eloquent пустой `avatar_url` заполняется локальным DiceBear SVG в формате data URI. Используются стиль Lorelei, размер `128` и UUID сотрудника как seed: одинаковый UUID даёт одинаковый результат при одинаковой версии библиотеки. Внешние HTTP-запросы и отдельное файловое хранилище не нужны.

Явно переданный аватар сохраняется. Генерация относится только к `Employee`, не к `User`; вставки через сырой SQL или Query Builder не вызывают Eloquent-событие. `EmployeeSeeder` вызывает генератор отдельно, поскольку общие сиды отключают model events. API отдаёт значение в `employees[].avatarUrl`.

## Диагностика

| Симптом | Что проверить |
| --- | --- |
| Docker не отвечает | Запущен ли Docker daemon / Docker Desktop |
| `port is already allocated` | Заняты ли `APP_PORT` или `DB_PORT`; измените параметр и пересоздайте контейнеры |
| PostgreSQL `unhealthy` | `make logs SERVICE=db`; совпадает ли порт `PGPORT`, хватает ли места, совместим ли существующий том с PostgreSQL 18 |
| `app` не становится healthy | `make logs SERVICE=app`: установка Composer, подключение к БД, миграции, доступность `btree_gist` и запись в `storage/` / `bootstrap/cache/` |
| Ошибка пароля БД после изменения `.env` | Значения окружения и учётные данные уже созданной БД должны совпадать |
| Все запросы графика дают `404` | `SCHEDULE_DEMO_MODE`, UUID исходного графика и выполненная инициализация |
| Запись возвращает `409` | Прочитайте актуальный календарь; проверьте версию и пересечения назначений |
| Браузер блокирует запрос, а curl работает | Точный origin в `CORS_ALLOWED_ORIGINS`, протокол/порт и кеш конфигурации |
| Ответ `429` | Учитывайте `Retry-After`; проверьте лимит, общий внешний IP и доверенные прокси |
| Тесты не находят БД | Выполните `make test-db` или используйте `make test`; проверьте права пользователя на создание БД |

В локальном окружении при ошибке `500` в API графика найдите `details.requestId` в `storage/logs/laravel.log`; в production смотрите логи контейнера приложения. Не удаляйте том PostgreSQL ради устранения ошибки запуска без резервной копии нужных данных.

### Образ и HTTPS

Production-образ собирается для `linux/amd64` на базе `dunglas/frankenphp:1-php8.5-bookworm`. Он содержит исходники и зависимости из `composer.lock` без dev-пакетов. Composer выполняется при сборке, а не при старте сервера. Локальные `.env`, секреты, логи и кеши не копируются в образ. PHP работает от `www-data`, с production-настройками и отключённым выводом ошибок; приложение использует `APP_ENV=production`, `APP_DEBUG=false` и логи в stderr.

При старте production entrypoint требует уже заданные `APP_KEY`, `DB_PASSWORD` и `SERVER_NAME`, кеширует конфигурацию, запускает `app:initialize`, затем кеширует маршруты и Blade-шаблоны. Существующий ключ не генерируется заново. Автоматические миграции и идемпотентные сиды работают так же, как описано выше.

Caddy обслуживает PHP и HTTPS. В [Caddyfile](docker/production/Caddyfile) настроен ACME Let's Encrypt с профилем `shortlived`; Caddy получает доверенный сертификат для `SERVER_NAME` и продлевает его автоматически. Данные ACME и сертификаты сохраняются в томе `caddy_data`, служебная конфигурация — в `caddy_config`. Серверу нужны доступные снаружи TCP-порты `80` и `443`; дополнительно опубликован UDP `443` для HTTP/3. HTTP перенаправляется на HTTPS. Внутренний healthcheck использует `/up` на `127.0.0.1:8080` внутри контейнера и не зависит от готовности сертификата.

Для HTTPS-запросов по IP браузеры не передают SNI. Настройка Caddy `default_sni` выбирает сертификат для `SERVER_NAME`, даже когда соединение приходит через внутренний адрес Docker.

PostgreSQL не публикует порт на сервере: приложение обращается к нему через внутреннюю Docker-сеть. Тома `postgres_data` и `app_storage` сохраняют БД и файлы приложения при смене образа. Запросы ограничены по размеру до `1 MB`; rate limit Laravel продолжает действовать.

### Серверные файлы и секреты

На сервере используются следующие пути:

| Путь | Назначение |
| --- | --- |
| `/opt/shiftschedule/compose.production.yaml` | Установленная production-конфигурация Compose |
| `/etc/shiftschedule/app.env` | Постоянные настройки и секреты приложения; владелец `root`, права `600` |
| `/usr/local/sbin/shiftschedule-deploy-gateway` | Ограниченная точка входа для CI по SSH, из `docker/deploy/gateway.sh` |
| `/usr/local/sbin/shiftschedule-deploy` | Root-скрипт установки образа, из `docker/deploy/deploy.sh` |
| `/etc/sudoers.d/shiftschedule-deploy` | Разрешение пользователю деплоя запускать только deploy-скрипт через sudo |
| `/var/lib/shiftschedule/current-image` | Тег последнего активированного образа |
| `/var/lib/shiftschedule/previous-image` | Предыдущий тег после успешной смены образа |
| `/var/backups/shiftschedule/` | Резервные копии PostgreSQL перед деплоем |

[.env.production.example](.env.production.example) — шаблон серверной конфигурации. При первичной установке администратор копирует его в `/etc/shiftschedule/app.env`, заполняет пустые `APP_KEY` и `DB_PASSWORD` и устанавливает права `600`. Реальные значения не размещаются в репозитории и не передаются GitHub Actions. `APP_KEY` генерируется один раз и сохраняется между релизами; пароль должен совпадать с учётной записью уже созданной PostgreSQL.

Compose получает один и тот же серверный файл через `--env-file` для подстановки параметров и через `env_file` для окружения приложения. CI передаёт только тег образа и его содержимое. Значение `APP_IMAGE` в shell имеет приоритет над значением из файла; для обслуживания уже запущенного релиза его нужно прочитать из `current-image`.

Пользователь `shiftschedule-deploy` не входит в группу Docker. Ключ CI в `/home/shiftschedule-deploy/.ssh/authorized_keys` ограничен параметрами `restrict` и `command="/usr/local/sbin/shiftschedule-deploy-gateway"`: PTY и forwarding отключены, произвольный shell не предоставляется. Gateway принимает только `deploy <40-символьный SHA>` и вызывает `sudo -n /usr/local/sbin/shiftschedule-deploy <SHA>`. Административное обслуживание выполняется отдельным доступом, не ключом CI.

Инфраструктурные файлы устанавливаются администратором отдельно от workflow. Изменения исходников, Dockerfile, PHP-настроек, Caddyfile и entrypoint попадают в новый Docker-образ автоматически. Изменения `compose.production.yaml`, SSH gateway или deploy-скрипта **не копируются на сервер самим CI**: обновите соответствующие серверные файлы, проверьте владельцев и права. Изменения sudoers проверяйте через `visudo -cf /etc/sudoers.d/shiftschedule-deploy`. Это предотвращает расхождение ожидаемой конфигурации с фактически установленной.

### GitHub Actions

Workflow **Test, build and deploy API** запускается на pull request в `master`, push в `master` и вручную через **Actions → Test, build and deploy API → Run workflow**. Для ручного production-деплоя выбирайте `master`. Pull request выполняет проверки и сборку, но не развёртывает приложение.

В **Settings → Secrets and variables → Actions → Secrets** задаются:

| Secret | Содержимое |
| --- | --- |
| `DEPLOY_SSH_KEY` | Закрытый ключ отдельного пользователя деплоя, публичная часть которого установлена с ограничением команды |
| `DEPLOY_KNOWN_HOSTS` | Запись `known_hosts` для SSH-сервера с заранее проверенным ключом хоста |

SSH использует `StrictHostKeyChecking=yes`; при изменении ключа сервера сначала проверьте новый отпечаток доверенным способом, затем обновите secret. Содержимое закрытого ключа не нужно добавлять в исходники, README или логи.

Необязательные **Variables**:

| Variable | По умолчанию | Назначение |
| --- | --- | --- |
| `DEPLOY_HOST` | `148.253.210.13` | Адрес SSH-сервера |
| `DEPLOY_USER` | `shiftschedule-deploy` | Пользователь ограниченного SSH-доступа |
| `DEPLOY_URL` | `https://test.api.shift-schedule.videoscale.pro` | Публичный адрес для проверки HTTPS и ссылки environment |

Deploy job использует GitHub environment `production`. Секреты и переменные можно задать на уровне репозитория либо этого environment. `APP_KEY` и пароль рабочей БД остаются только на сервере.

Последовательность pipeline:

1. Поднимается отдельный PostgreSQL 18 с БД `shiftschedule_testing`, собирается test target Dockerfile.
2. Выполняются `composer validate --strict` и весь PHPUnit-набор на настоящем PostgreSQL. Рабочий сервер в этих тестах не участвует.
3. Собирается production-образ `shiftschedule-api:<commit SHA>` с меткой `org.opencontainers.image.revision`. Для `master` образ сохраняется в сжатый tar и загружается как GitHub Actions artifact на один день.
4. Deploy job скачивает этот образ и передаёт его по SSH в stdin команды `deploy <SHA>`. Docker registry не используется.
5. Серверный скрипт берёт файловую блокировку, загружает образ, проверяет его revision, поднимает БД и делает резервную копию. Затем пересоздаёт приложение и ждёт внутреннего healthcheck.
6. После успешной активации записываются `current-image` и, при смене версии, `previous-image`. CI проверяет публичные HTTPS-адреса `/up`, `/api/v1`, `/docs`, `/docs/openapi.json` и календарь демонстрационного графика. В summary запуска появляются ссылки на API и Swagger.

Следующий push в `master` повторяет весь процесс. Параллельные деплои одной ветки сериализуются GitHub concurrency; сервер дополнительно использует `flock`. Артефакт содержит уже собранный образ, а не команды для произвольного исполнения на сервере.

Публичная проверка текущего workflow ожидает `API_DOCS_ENABLED=true` и `SCHEDULE_DEMO_MODE=true`. При отключении Swagger или demo-доступа адаптируйте проверяемые маршруты. Проверка HTTPS и календаря выполняется **после активации**: её ошибка помечает workflow как failed, но сама по себе не откатывает уже запущенный релиз.

### Обслуживание на сервере

```sh
compose_prod up -d --no-deps --force-recreate --wait --wait-timeout 240 app
```

Эта команда запускает entrypoint и миграции, но не вызывает deploy-скрипт с резервным копированием; перед ручными операциями, меняющими схему или данные, сделайте отдельную копию БД. Для нового кода используйте pipeline, а не редактирование файлов внутри контейнера. Логи PHP и HTTP доступны через `compose_prod logs`; Compose ограничивает размер контейнерных логов.

### Резервные копии и откат

Перед каждой активацией образа deploy-скрипт выполняет `pg_dump --format=custom` и сохраняет результат в `/var/backups/shiftschedule/<UTC-время>-<commit SHA>.dump`. Каталог доступен только root с правами `700`, файлы создаются с правами `600`. Непустая копия обязательна для продолжения деплоя. При первой установке копия может содержать ещё пустую рабочую БД до первоначальных миграций.

Автоматическая очистка и вынос этих копий на другой сервер не настроены: контролируйте свободное место и организуйте внешнее хранение отдельно. Копия БД не включает содержимое `app_storage` и Caddy-томов.

Если контейнер приложения не проходит внутренний healthcheck при деплое, скрипт пытается вернуть предыдущий образ. **Миграции БД автоматически не откатываются**, поэтому возврат старого кода с новой схемой может оказаться несовместимым. Ошибка публичной HTTPS-проверки после успешного внутреннего healthcheck автоматический возврат не запускает.

Для ручного возврата сначала проверьте совместимость старой версии с текущей схемой и наличие резервной копии. В root-shell с объявленной выше функцией `compose_prod`:

```sh
export APP_IMAGE="$(cat /var/lib/shiftschedule/previous-image)"
docker image inspect "$APP_IMAGE" > /dev/null
compose_prod up -d --no-deps --wait --wait-timeout 240 app
```

После успешного healthcheck и проверки API зафиксируйте выбранный образ как текущий:

```sh
printf '%s\n' "$APP_IMAGE" > /var/lib/shiftschedule/current-image.next
mv /var/lib/shiftschedule/current-image.next /var/lib/shiftschedule/current-image
```

Возврат образа сохраняет PostgreSQL и её текущую схему. Если требуется восстановить дамп, это отдельная административная операция с выбором нужной копии и оценкой потери изменений после её создания; deploy-скрипт её не выполняет. Не используйте `docker compose down -v` для перезапуска или отката: это удалит постоянные тома.

### Смена домена или адреса API

1. Настройте DNS домена на сервер и доступность портов `80` / `443`.
2. В `/etc/shiftschedule/app.env` задайте `SERVER_NAME=api.example.com` и `APP_URL=https://api.example.com`. Сохраните существующие `APP_KEY` и данные доступа к БД.
3. В `CORS_ALLOWED_ORIGINS` перечислите origin клиентского приложения. Для текущего GitHub Pages это `https://toxanetoxa.github.io`, без пути репозитория. Домен API не является origin клиентского приложения.
4. Пересоздайте `app` командой обслуживания выше. Caddy использует новый `SERVER_NAME` для HTTPS; не удаляйте его постоянный том.
5. Обновите backend-переменную GitHub Actions `DEPLOY_URL`, чтобы CI проверял новый адрес. `DEPLOY_HOST` можно оставить IP, если SSH по нему сохраняется.
6. В репозитории клиентского приложения задайте variable `VITE_API_BASE_URL=https://api.example.com/api/v1` и повторно запустите его workflow публикации: адрес API встраивается в клиентскую сборку.

Для текущего домена клиенту нужен `VITE_API_BASE_URL=https://test.api.shift-schedule.videoscale.pro/api/v1`. Серверные `SERVER_NAME` и `APP_URL`, а также переменная CI `DEPLOY_URL` должны указывать на этот же домен; SSH-переменная `DEPLOY_HOST` остаётся `148.253.210.13`.

Production-конфигурация оставляет демонстрационный режим: посетители могут читать и менять один общий график без входа. Для реальных пользователей необходимо добавить аутентификацию и проверку прав; выключение demo mode само по себе закрывает маршруты графика. `app:initialize` продолжает выполнять исходные сиды, включая тестовую запись пользователя.
